---
name: shipmaster
description: "Ship a batch of GitHub issues for you: one ship per issue, one at a time or N at once, each unblocked issue starting as soon as a slot frees."
disable-model-invocation: true
---

You do what the user otherwise does by hand: ship an issue, wait for it to merge, check what is unblocked, ship the next. A **ship** is a background subagent of this session that runs the `ship` skill on one issue in its own worktree: it builds, reviews and merges. You coordinate. You read GitHub, start and resume ships, pass their questions to the user, and pace their merges. The code, reviews, PRs and issue updates all belong to the ships.

The arguments hold the issues (numbers, `owner/repo#n` or URLs, all in this checkout's repo) and, sometimes:

- **a count** ("3 concurrent", "4 at once"): keep that many ships live. Without one, the count is 1 and issues ship one by one.
- **workers** ("use worker-routing", "with workers"): each ship gets `with workers`, so it builds, fixes and runs devices through Claude subagents, routed like its reviewers by the `worker-routing` skill.

A ship is **live** from its start until it merges or stops; one waiting on the user is live. Ships run in auto permission mode, so run this only from a session in auto mode; otherwise stop and say so.

**Ship default.** Every ship runs on the model and effort in `~/.claude/shipmaster-defaults` on this machine (`model=<id>` and `effort=<level>` lines), and on Opus 5.5 at medium where the file names none; your own model does not carry over. The Agent tool takes a model family, not an id, so pass the family named in the id (`claude-opus-5-5` is `opus`; likewise `sonnet`, `haiku`, `fable`), which runs that family's current model. When the file names an effort outside low, medium, high, xhigh and max, or an id that names none of those families, start no ship: report the line and stop. When the arguments set the default instead of naming issues ("set default to sonnet 5.5 high"), write that file with the model's full id (Opus 5.5 is `claude-opus-5-5`) and an effort of low, medium, high, xhigh or max, keeping the current effort when the user names none. Read it back, report the model and effort and that the setting is for this machine only, and stop. A ship keeps the model it started on, so only ships started after the change use it.

## 1. Plan

First check that the skills are current, since every ship reads them at its start: `git -C ~/.claude/skills/shipmaster fetch -q`, then `git -C ~/.claude/skills/shipmaster status -sb`. When the clone is on its default branch and behind it, say so and run `git -C ~/.claude/skills/shipmaster pull --ff-only` before any ship starts. When it is on another branch, cannot fast-forward, or holds local changes, stop and tell the user.

For each issue read `gh issue view <n> --json number,title,state,body` and its blockers, `gh api repos/<owner>/<repo>/issues/<n>/dependencies/blocked_by --jq '.[] | {number, state}'`, plus any `Blocked by: #a, #b` line in the body. Note the issue's **open PR**, if one exists: an open PR whose body names `#<n>` (`gh pr list --state open --json number,headRefName,body`). Without one, note its **earlier branch**, if one exists: after `git fetch origin`, a remote `ticket/<n>-*` branch (`git ls-remote --heads origin 'refs/heads/ticket/<n>-*'`), other than the one in its `ships/<n>/ship` file, with commits not on `origin/<default>` (`git rev-list --count origin/<default>..origin/<branch>`) and no PR in any state (`gh pr list --head <branch> --state all`); with several, take the one with the newest commit and name the rest in the plan. A closed issue is reported and dropped. An issue is **unblocked** when every blocker is closed. An issue is **stuck** when a blocker is open and outside the batch, stuck itself, or has a ship that merged or stopped without closing it; report it with that blocker. Recheck this on every wake.

Order the batch blockers first, otherwise in the user's order. State the plan in a few lines (the order, what starts now, what waits on what, what is stuck, each open PR or earlier branch a ship will take over, and any open PRs outside the batch), write the order and the count to `ships/batch` in the session scratchpad, and go straight on to step 2. When the user adds issues later, plan them the same way and append them to the order.

Done when every issue is ordered or reported.

## 2. Launch

Each ship keeps its state in `ships/<n>/` in the session scratchpad: a `ship` file with the lines `agent=<agent id>`, `launch=<process id>`, `branch=<branch>` and `worktree=<absolute path>`, then one `<k>.msg` per message you send it and one `<k>.reply` per reply it hands back, `k` counting from 1. Write each reply to its file, word for word, as soon as it arrives: your context may be summarized later, and the files are what you rebuild from. An issue whose `ship` file exists has its ship; it never gets a second one.

While live ships are fewer than the count, take the next unblocked issue in plan order without a ship:

1. **Worktree.** Create one on a new branch `ticket/<n>-<slug>` (slug: a few words of the title, kebab-case) from the latest `origin/<default>`, with the repo's own worktree command where its instructions name one (jj: `scripts/worktree-new.sh ship-<n> <branch>`, which also installs and links the backend), otherwise `git fetch && git worktree add -b <branch> .claude/worktrees/ship-<n> origin/<default>`. An issue with an open PR uses that PR's head branch instead, based on `origin/<head branch>` (`git worktree add -b <branch> <path> origin/<branch>`, or the repo command with that base). An issue with an earlier branch gets the new ticket branch based on `origin/<earlier branch>`, with `-2` added to its name when it would match the earlier branch's, which stays as it was. Take its absolute path from `git worktree list`, and write the `ship` file's `branch` and `worktree` lines.
2. **Brief.** Write `1.msg` with the Write tool, brackets filled:

   > Ship issue #[n] in [owner/repo]. Read `~/.claude/skills/ship/SKILL.md` and follow it, with the arguments `[n][ with workers]`, except where this prompt says otherwise. Your worktree is `[worktree]`, already on the ticket branch `[branch]`; use it. Your shell starts in another folder and does not keep a `cd` between commands, so begin every Bash command with `cd [worktree] && { [ ! -f .env.worktree ] || . ./.env.worktree; } && `, and give file tools absolute paths inside the worktree. Every subagent you start, and every one a skill you call starts (`tdd`, `code-review`, the reviewers), begins in that other folder too, so put the same rule, with this worktree's path, in each brief.[ Open PR only: Open PR #[pr] on that branch already holds work for this issue: take it as yours, finish what the issue still needs, and carry on from step 3 with that PR instead of opening another.][ Earlier branch only: Your branch starts from `[earlier branch]`, which holds earlier commits for this issue with no PR: take them as yours, bring the branch up to date with `origin/[default]`, and finish what the issue still needs.] You run in the background, and the report you hand back when a turn ends is all the shipmaster sees, so end it with the lines below where they apply. Nobody can answer mid-turn: wherever ship says to ask the user, end your turn with `waiting on the user: <question>`, and the answer comes as your next message. The user started this batch, and through it authorizes the GitHub writes that ship and the repo's issue rules call for: comments, labels, ticked criteria and closing, on issue #[n], on your PR, on one new issue for your PR's review follow-ups, and, after the merge, on any issue outside this batch that your PR fixes, which you close only with evidence that it is fixed. When such a write is refused anyway, end your turn with `waiting on the user: <the refused command and why it is needed>`. Run only the device lanes the lane selector says to run on the pull request; for "every lane" that is its `run on the pull request:` line, and the full run before the next release build covers the rest. Say which in your checks comment. Only the holder of the baton may run anything on a phone, emulator or Simulator, since other ships use them too. You hold it only while a message that hands it to you is your latest, and it passes back when your turn ends. Before such a device run without it, end your turn with `needs the baton: <the run>`. Once you hold it, end your turn as soon as that run finishes, with `device run done: <result>`, so the baton passes on while you wait to carry on. Before you end any turn, stop every server or other background process you started, so none is left holding a port or the worktree.[ Count above 1: Other ships run beside you on this machine, and only the holder of the baton may merge. When the PR is green at step 5, end your turn with `ready to merge <PR url>` instead of merging.]

3. **Start** it with the Agent tool: `subagent_type` `general-purpose`, `description` `ship #<n>`, `model` and `effort` from the ship default, and the text of `1.msg` as the prompt. Write the agent id the tool returns to the `ship` file's `agent` line, and this session's process id (`$CLAUDE_PID`, which changes on every start or resume of the session) to its `launch` line.

To **resume** a ship, write the message to the next `<k>.msg`, send that text with SendMessage to the ship's agent id, and write this session's `$CLAUDE_PID` to the ship's `launch` line (load SendMessage and TaskStop with ToolSearch first when they are deferred). When the Agent or SendMessage call fails, write its error as that turn's `<k>.reply`. The ship carries on with its whole context. When a ship's turn ends, its reply reaches you and wakes you.

## 3. Each wake

On every wake and every user message, rebuild the state from GitHub and `ships/`; they hold everything, so nothing depends on your memory of earlier turns. A ship's reply is its latest `<k>.reply`. Give each ship the first state that matches:

1. **working**: its latest `<k>.msg` has no `<k>.reply` yet, its `ship` file has an `agent` line, and its `launch` line is this session's `$CLAUDE_PID`. Ships end with the session process that started them, so after a restart or resume a ship with no reply is stopped.
2. **waiting**: its reply ends with `waiting on the user: <question>`, even after its PR merged (a refused write after the merge asks this way). Pass the question to the user word for word, with the issue, once per reply. Resume the ship with their answer as they wrote it.
3. **merged**: `gh pr list --head <branch> --state merged` finds its PR. Remove its worktree with `git worktree remove <path>` to free the disk: its commits are on the default branch, and ship copies its evidence out before merging. Only a dirty worktree stays, since uncommitted edits are on no branch; report it.
4. **ready**: its reply ends with `ready to merge <PR url>`.
5. **needs the baton**: its reply ends with `needs the baton: <the run>`.
6. **device run done**: its reply ends with `device run done: <result>`.
7. **stopped**: anything else: an error, five review rounds without a clean one, a ship with no reply after this session restarted or resumed, or a ship whose agent can no longer take a message. Report its last reply.

**Never message a working ship**: a second message mid-turn would mix two turns in one worktree. Where an action below would resume it, wait for its reply. While any ship is working, keep one background `sleep 7200` command running (`<task id> <$CLAUDE_PID>` in `ships/sleep`; start another once that one has ended, and a sleep started under another `$CLAUDE_PID` has ended), so a wake comes even when no ship replies. A ship that has worked for two hours with no new commit or PR activity may be stuck; tell the user, and stop it with TaskStop only on their word, then write `stopped by the user` as that turn's `<k>.reply`.

Then act, in this order:

1. **Pass the baton.** The **baton** is the one right to merge or use a device; it keeps two ships off one emulator and keeps merge checks and device runs from loading the machine at once. When no working ship's latest message handed it over, give it to the earliest ready ship in plan order ("You hold the baton: merge now, carrying on from step 5."), or else to the earliest ship that needs it ("You hold the baton: do that run."), by resuming that ship. A ship hands it back as soon as its run ends, so a merge never waits behind the rest of another ship's work.
2. **Carry on.** Resume every ship whose device run is done with "Carry on from where you stopped."; it no longer holds the baton.
3. **Train.** The **train** is one full device run on the default branch that covers every ship merged since the last one. Start one only where the repo's docs ask for a full run after merges; skc-workspace runs its full device run only before a release build (`skc-mobile/docs/tier2-lane.md`, "A full run"), so there a shipmaster starts no train. Where one is due, start it when no ship holds the baton, hand the baton to no ship until it ends, and wait for its result with a background command that ends when the run does. When it is red, open one issue naming each failing lane, its log, and the PRs merged since the last green train.
4. **Launch.** Run step 2 for every slot that is free.
5. **Tell.** One line per change since the last wake: merged, waiting with its question, a device run's or a train's result, stopped with its reason.

When no ship is live, none can launch and no train is due or running, go to step 4. Otherwise end your turn.

## 4. Report

One line per issue: merged (its PR, and its worktree if it stayed dirty), stuck (its blocker), stopped (its reason), or waiting (its question). Ships live inside this session: an idle ship carries on only through a message from here, and they all end when this session does.
